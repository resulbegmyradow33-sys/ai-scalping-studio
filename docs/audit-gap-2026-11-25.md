## Verdict in one paragraph

The library work since the addendum is real and mostly well-defended: fold
evidence, a one-shot holdout ledger, a named fail-closed promotion policy, a
provenance-checked paper champion reader, five orchestrator handlers, a daemon
with a measured guard, and a bundle producer now exist in code and pass their
tests. On `main` none of it has a runtime call site for promotion, no orchestrator
job has ever run, and no paper session or holdout spend exists.

One real-data attempt does exist, but it is a **branch-only, hand-driven CLI
sequence**, not a mainline feature: `.worktrees/v1/.worktrees/realaccept`
(branch `feat/realaccept`, commit `fcd6f4f`, base `50fbca6`, run 2026-11-25).
It validated 29,586 XAUUSD H1 bars, built dataset `439ad79658c7`, ran 22 gated
trials to `no_trade`, persisted evidence for a gate-rejected candidate,
reproduced the bundle exactly, evaluated `PROMOTION_V1` (rejected, including
`missing_locked_oos`), and refused paper with `NoChampionError`. That record is
committed there as `docs/acceptance-attempt-2026-11-25.md` and
`docs/evidence/acceptance-attempt-2026-11-25.json`. It did not spend the holdout
and did not promote. The branch is not merged, its own record says the next
step needs owner approval, its bundle lives under a gitignored
`backend/runs/realaccept/`, and the summary is committed only on that branch.
So the accurate status is "operated once by hand on a side branch and stopped
at the promotion gate", not "never operated".

## Implemented-and-tested vs validated-and-used

### 1. Do discovery folds and a locked holdout exist, and has a holdout ever been spent on real data?

Folds: yes. `build_evidence` cuts `>= 3` expanding, non-overlapping folds from
the train+validation timeline, with a purge/embargo gap before each test block,
cost-stress reruns, regime attribution and bootstrap intervals. Fail-closed
codes (`insufficient_folds`, `missing_cost_stress`, `holdout_dataset`,
`frame_mismatch`, `fold_trades_below_minimum`, …) are exercised in
`tests/test_discovery_evidence.py` and `tests/test_evidence_adversarial.py`.

Holdout: the protocol and ledger are implemented and tested, but the only
non-test caller is the synthetic acceptance harness
(`src/scalping/acceptance/run.py:724-765`). It seals a ledger under a temp
`run_dir` with `actor="acceptance"` against a synthetic store, and evaluates it.
There is no CLI command, orchestrator handler or documented operator step that
seals or unlocks a holdout, and no holdout ledger file exists in the repository
or any worktree. The repository's own doc states no real XAUUSD holdout has been
spent (`docs/backtesting-methodology.md:387-392`).

Consequence: a real-data bundle built today necessarily rejects with
`missing_locked_oos` under `PROMOTION_V1` (require_locked_oos=True). That
rejection is correct and expected. The gate has now rejected one real bundle
(§2), but it has never accepted one: no real-market bundle has carried a locked
OOS section (only the synthetic acceptance harness attaches one).

### 2. Is promotion fail-closed, and has any candidate been promoted or rejected through the real policy outside tests?

Fail-closed by construction: `PROMOTION_V1` is non-empty and versioned; the
production registry maps only its digest (`promotion.py:373`); a copied/edited
policy is refused (`non_production_policy`, `:1949`); `require_locked_oos` is
true; no force flag exists; missing/stale/mismatched identity, insufficient
folds/trades, cost stress, regime coverage, CI, complexity and trial caps all
reject; archive-side promotion re-verifies the stored bundle and the accepted
trial's dataset/settings (`archive.py:1684+`).

Call sites on `main`: none outside tests. `promote_with_evidence` is referenced
only from `promotion.py`, `archive.py` (docstring), the acceptance decision path
(which does not promote) and tests. The CLI has `discovery run|reproduce|evidence`
only (`cli.py:1713-1852`); no `promote`. A refusal writes no archive row, and a
`PromotionDecision` cannot be reconstructed after the process exits because the
seal is a random per-process HMAC (`promotion.py:487-498`).

Runtime: one real attempt exists on the `feat/realaccept` branch. It called
`promote_with_evidence` twice on a real H1 bundle: the test-policy attempt was
refused with `non_production_policy`, and `PROMOTION_V1` refused the same bundle
with seven codes (`min_positive_fold_fraction`, `min_expectancy_r`,
`min_profit_factor`, `min_ci_lower_r`, `cost_stress`, `stress_degradation`,
`missing_locked_oos`). The archive has 0 promotions and 0 champions. So the real
policy has rejected real evidence once and has never accepted any candidate.

Before that, the H1 smoke's best candidate was flat and evidence construction
refused it with `fold_trades_below_minimum`; decision `no_trade`
(`docs/evidence/discovery-smoke-2026-11-24.json`, `promotion_attempted:false`).

### 3. Do the orchestrator handlers and daemon form a real end-to-end chain outside tests?

The orchestrator queue has never run; a chain did run once, by hand, on the
`feat/realaccept` branch: `data validate → dataset build → discovery run →
discovery evidence → discovery reproduce → promotion script → paper gate`, each
as a separate CLI/script call with exit codes recorded in
`docs/acceptance-attempt-2026-11-25.md`. That proves the stages connect on real
bars; it does not exercise triggers, job dependencies, retries or the daemon.
The CLI can build those pieces (`cli.py:1237-1320` registers
the five handlers; `:1907-1968` builds the daemon, default DB
`runs/orchestrator.sqlite3`, default profile `m2_8gb`). No such database, event
log or status snapshot exists in this checkout or any local worktree.

The wiring is also incomplete for the intended loop:

- `dataset.build` does not enqueue `discovery.run`;
- `discovery.run` only records a decision; it does not build or persist an
  evidence bundle (that is the separate `discovery evidence` CLI);
- no handler runs the holdout or a champion review, so promotion cannot happen
  in the queue at all (`docs/orchestrator.md` says the same);
- the approved-proposal → `discovery.run` bridge exists as a class but is not
  bound by the daemon CLI, and there is no CLI/API to approve a proposal;
- `paper.outcomes` is registered with the default `should_queue=None`, so a
  matured batch records a proposal and stops.

`tests/test_orchestrator_integration.py` is honest about this: its real
dependency chain is `knowledge.ingest → dataset.build`, and its `paper.advance`
assertions are "no champion ⇒ NO TRADE". That is good coverage of seams, not an
end-to-end autonomous run.

### 4. Does paper advance use a real evidence champion, and has a real session run with immutable attribution?

The code path is correct: `ChampionProvider` refuses a missing champion,
non-evidence mode, a policy digest outside the production allow-list, and a
payload that does not hash to its archived id (`champion.py:162-211`). The
`paper.advance` handler turns those refusals into NO TRADE results with reason
classes (`no_champion`, `no_evidence_champion`, `invalid_champion`).

But no real evidence champion exists: every test champion is seeded through
`promote_for_tests` with a test policy and `require_production=False`
(`tests/promotion_support.py`). Even the synthetic acceptance harness bypasses
the provider: its paper stage constructs `AutonomousPaperRunner` with a spec
directly (`acceptance/run.py:797-810`). The branch attempt reached the same
wall on real data: the paper gate returned `NoChampionError: no champion in
scope 'XAUUSD:H1'` and created no ledger. No paper ledger exists on disk
anywhere, and the bench harness could not even advance paper on real bars
(`BarGapError`).

So: the governed path is implemented and unit-tested; it has never carried a
real session, and no trade anywhere carries immutable attribution from a real
run. The ledger's attribution design (spec hash as `model_version`, appended
bars, outcome fingerprint over `strategy_hash`/`dataset_id`/`source`/
`synthetic`, no trade UPDATE path) is nevertheless the right foundation.

## Top 5 remaining risks

1. **Provenance is not part of promotion evidence.** `DatasetManifest`,
   `CandidateEvidence` and `PROMOTION_V1` carry no `source`/`synthetic` field
   (grep: zero matches in `datasets/builder.py`, `discovery/evidence.py`,
   `discovery/promotion.py`). The provenance audit's S1 finding
   (`docs/provenance-audit-2026-11-24.md:110`) still holds: synthetic or
   relabelled data can satisfy every policy check. Synthetic rejection currently
   lives only at the paper-outcome trigger, after promotion.

   *Update 2026-11-25 (`feat/prov2`, local branch):* the fields now exist on
   `DatasetManifest`, `EvidenceConfig`, `CandidateEvidence`, `LockedOOSEvidence`
   and the holdout seal; evidence schema 4 includes them in the checksum;
   `PROMOTION_V1` refuses `synthetic is None` (`provenance_unknown`) and
   `synthetic is True` (`synthetic_data`), and only a non-production policy may
   opt in. See `docs/provenance-audit-2026-11-24.md` §0. What remains is the
   self-declared sidecar (no producer attestation) and the paths that still do
   not record provenance they could know.
2. **Trial accounting is self-declared.** `discovery evidence --trials/--search-budget`
   are free arguments; the promotion policy caps the numbers it is given but
   never checks them against the archive's actual evaluations. The one real
   module that could deflate for selection (`discovery/selection.py`) is unused.
   Understating trials converts the multiple-testing gate into a formality.
3. **No production promotion entry point, and no durable decision.** Promotion
   and the holdout are library-only; the only real attempt is a hand-written
   script in a side branch (`runs/realaccept/promotion_eval.py`). Decisions are
   sealed with a per-process HMAC and cannot be persisted/re-verified; refused
   promotions are not audited. Closing this needs an explicit reviewed command
   (and an audit table for refusals), not a test helper or a scratch script.
4. **The orchestrator is five handlers, not a pipeline.** New data stops at
   `dataset.build`; the one real chain was a sequence of CLI calls, and the
   queue has never drained a real job. There is no evidence job, no
   champion/holdout job, no bound proposal trigger, no proposal approval
   surface, and no `should_queue` policy for matured outcomes. Unattended
   operation cannot reach paper.
5. **Selection is still single-window.** Folds evaluate a fixed spec after the
   search chose it on one validation slice; the majority-outside-selection rule
   mitigates but does not remove the winner's curse. Combined with an iid
   bootstrap and no parameter-neighbourhood or cross-symbol sweep, a passing
   bundle could still be a friendly sample. One holdout pass is one sample and
   binds one spec per dataset build.

## What a reviewer should not believe yet

- **"Fail-closed promotion" does not mean "market-ready gate".** It means the
  policy rejects missing/stale/thin evidence. It has rejected one real bundle
  (on a branch) and never accepted one; it still cannot verify the declared
  trial count. Data provenance is now a policy input on `feat/prov2`, but a
  "real" sidecar is still self-declared.
- **"Multiple-testing control"** exists as `discovery/selection.py` and as a
  trial cap; no shipped path consumes the selection report.
- **"Orchestrator end-to-end coverage"** refers to seam tests
  (`knowledge.ingest → dataset.build`) and a synthetic acceptance harness, not
  a queue-driven cycle on real data. The acceptance report itself sets
  `validated=false`, `paper_traded=false`, `profitable=false`.
- **"Paper trading"** has no session. The paper page, continuous runner and
  outcome reader are implemented; no ledger exists, and the M2 bench's paper
  stage failed on real bars.
- **"M2 measurements"** are one-time measurements at `693f8a3` on a branch,
  taken with a desktop session open, and explicitly `m2_acceptance=false`.
- **"Validated"** anywhere in an older document. No chronological OOS pass, no
  spent real holdout, no accepted promotion, no paper session, no profit sample.
- **Stale status lines in both directions.** `STATUS.md` understates paper
  governance (fixed in code) and overstates nothing; the addendum understates
  the producer and the autonomy page. Check code, not summaries.

## Bottom line

The project has moved from "no evidence machinery" to "evidence machinery that
has been operated once, by hand, and stopped exactly where it should". The next
milestone is not another module: it is an owner-approved, repeatable run on real
XAUUSD data that spends the locked holdout on a plausibly positive candidate,
produces an accepted promotion, runs a continuous paper session with attribution,
and turns matured outcomes into a queued proposal — with mainline commands and
kept artifacts. Until that exists, every claim above the word "implemented" is
unsupported.
